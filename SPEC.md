# SPEC: AI agent in GitHub Actions inside a Docker Sandbox (demo repo)

## 0\. Purpose

Build a small, self-contained GitHub repository that demonstrates the pattern described in Docker's blog post *"Running AI agents in GitHub Actions with Docker Sandboxes"* (Oleg Šelajev, Aug 21, 2026): [https\://www\.docker.com/blog/running-ai-agents-in-github-actions-with-docker-sandboxes/](https://www.docker.com/blog/running-ai-agents-in-github-actions-with-docker-sandboxes/)

The demo shows that a CI coding agent can be given broad freedom (root, arbitrary shell, its own Docker daemon) **inside** a disposable Docker Sandbox (`sbx`) microVM, while having a very narrow surface **outside** it (network allowlist, read-only GitHub token, PR creation restricted to `src/**` and handled by a separate job).

The concrete story the demo must reproduce:

1. A GitHub Actions workflow (authored with GitHub Agentic Workflows, `gh-aw`) starts an AI agent inside a Docker Sandbox on an `ubuntu-24.04` hosted runner.  
2. The agent records evidence of where it is running (`uname`, `docker version`, `docker info`, an Alpine container run).  
3. The agent runs a Java 21 integration test suite that uses Testcontainers to start PostgreSQL via the sandbox's **private** Docker daemon.  
4. The agent finds an intentionally seeded bug (case-sensitive email uniqueness), writes a regression test, applies the smallest fix, reruns the suite.  
5. A separate safe-output job opens a **draft** pull request containing only files under `src/**`.

Reference implementation for cross-checking (do not copy blindly, but consult if something is unclear): [https\://github.com/shelajev/docker-sandbox-gh-aw-demo](https://github.com/shelajev/docker-sandbox-gh-aw-demo)

## 4\. The application (with the seeded defect)

### 4.1 REQUIREMENTS.md

Short, plain-language document. Must state, unambiguously:

- Users register with an email address.  
- **Email addresses are case-insensitive.** `Alice@example.com` and `alice@example.com` identify the same user.  
- Registering an email that already exists (under that rule) must be rejected.  
- Leading/trailing whitespace handling: state explicitly either way (recommended: "surrounding whitespace is not significant") so the agent has a clear target. Keep it to one or two such rules; the headline invariant is case-insensitivity.

### 4.2 Schema

```sql
CREATE TABLE IF NOT EXISTS users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

The plain `UNIQUE` on `TEXT` is case-sensitive in PostgreSQL. That is part of the seeded defect. Do not use `citext` or a `lower(email)` index.

### 4.3 RegistrationService

- Constructor takes a `javax.sql.DataSource` (or a JDBC URL/user/password) and ensures the schema exists.  
- `boolean register(String email)` — inserts the email **exactly as provided**. Returns `true` if a new row was created, `false` if the insert hit the unique constraint (catch SQLState `23505`). Other SQL errors propagate as an unchecked exception.  
- Optionally `boolean isRegistered(String email)` and `int count()` helpers for tests.  
- **No normalization anywhere.** The intended one-line fix the agent should find is normalizing (e.g. `email.trim().toLowerCase(Locale.ROOT)`) before insert. Do not leave hints like `// TODO normalize` in the code.

### 4.4 Seeded integration test — RegistrationServiceIT

- Uses `@Testcontainers` \+ `@Container static PostgreSQLContainer<?>` with the pinned PostgreSQL image.  
- Contains exactly two tests (so that after the agent adds one, the post's "two passing integration tests"-style outcome is easy to read; adjust if you prefer, but keep the suite small):  
  1. `registersNewEmail` — first registration returns `true`.  
  2. `rejectsExactDuplicate` — registering the same string twice returns `true` then `false`.  
- Must **not** test case variants.  
- Each test should start from a clean table (truncate in `@BeforeEach`).  
- Configure Maven so these tests run in the `test` phase (e.g. name it `*IT` and configure Surefire includes, or name it `*Test`). The script in 5.1 runs `mvn test`, so whatever naming you choose must be picked up by `mvn test`.

### 4.5 pom.xml

- `maven.compiler.release` \= 21\.  
- Dependencies: PostgreSQL JDBC driver, JUnit Jupiter, Testcontainers BOM \+ `postgresql` \+ `junit-jupiter`, a simple SLF4J binding for tests (e.g. `slf4j-simple`) so Testcontainers logs are visible in CI output.  
- Pin all versions explicitly. Use current stable releases; verify they resolve.  
- Surefire configured to print test output to console (`useFile=false`, `trimStackTrace=false`) so the agent's failure messages (e.g. `expected: <false> but was: <true>`) appear in the workflow log.

## 5\. Running tests inside containers

### 5.1 scripts/test-in-docker.sh

Bash, `set -euo pipefail`, executable bit set, LF line endings. Behavior:

- Runs Maven inside the pinned `maven:3.9.9-eclipse-temurin-21@sha256:…` image with `--rm`.  
- Bind-mounts the repo to `/workspace` and sets it as the working directory.  
- Bind-mounts `/var/run/docker.sock` so Testcontainers inside the Maven container talks to whatever Docker daemon is local. Inside the sandbox, that is the sandbox's **private** daemon — this is the key isolation property of the demo.  
- Adds `--add-host=host.testcontainers.internal:host-gateway` and sets `TESTCONTAINERS_HOST_OVERRIDE=host.testcontainers.internal` so the Maven container can reach the PostgreSQL container's mapped port (sibling containers, not nested).  
- Mounts a named volume (or a directory under the repo that is gitignored) for `~/.m2` so repeated runs don't redownload the world. Keep it optional and simple.  
- Passes through any script arguments to Maven before the goal, e.g. `./scripts/test-in-docker.sh -Dtest=RegistrationServiceIT#rejectsExactDuplicate` runs `mvn --batch-mode <args> test`.  
- Exits with Maven's exit code.

Docker must be the **only** local prerequisite to run the tests (no local JDK/Maven required).

## 6\. The agentic workflow

### 6.1 .github/workflows/sandbox-explorer.md — frontmatter

The frontmatter must configure:

- `name`: something like `"Docker Sandboxes sample: exploratory test"`.  
- `on: workflow_dispatch` only (manual trigger; no push/PR triggers, so it never runs unexpectedly).  
- `runs-on: ubuntu-24.04`.  
- `permissions`: `contents: read` and `copilot-requests: write`. Nothing else. The agent's token must not be able to write to the repo.  
- `engine: copilot`.  
- `network.allowed`: `defaults`, `github`, `containers`, `java` (gh-aw ecosystem identifiers — needed for Copilot/GitHub APIs, pulling container images, and Maven Central).  
- `sandbox.agent`: `id: awf`, `runtime: docker-sbx`, `sudo: true`. These three lines are the integration the post is about; keep them visually prominent and commented.  
- `tools`: `edit:` enabled, and `bash` allowing all commands (`[":*"]`).  
- `safe-outputs.create-pull-request`: `title-prefix: "[docker-sbx sample] "`, `draft: true`, `protected-files: blocked`, `allowed-files: ["src/**"]`.

Before writing this, read the current gh-aw docs for exact key names and semantics, since the tool evolves quickly:

- Agent runtimes reference: [https\://github.github.com/gh-aw/reference/agent-runtimes/\#docker-sbx](https://github.github.com/gh-aw/reference/agent-runtimes/#docker-sbx)  
- gh-aw repo: [https\://github.com/github/gh-aw](https://github.com/github/gh-aw)

If any key has changed, follow the docs and note the deviation in the README.

### 6.2 sandbox-explorer.md — body (the agent's task prompt)

Write the prompt in your own words. It must instruct the agent to act as a **bounded exploratory tester** and, in order:

1. **Record the environment** before touching code: `uname -a`, `docker version`, `docker info`, and `docker run --rm alpine:<pinned> uname -a` (pin Alpine too). Print the output so it lands in the workflow log as evidence the work ran inside the microVM with a private daemon.  
2. Read `REQUIREMENTS.md` and the relevant source and test files.  
3. Run `./scripts/test-in-docker.sh` unchanged as a baseline, and report the result.  
4. Add a PostgreSQL Testcontainers test that registers two addresses differing only in letter case (e.g. `Alice@example.com` then `alice@example.com`) and asserts the second is rejected.  
5. Run that focused test and explain the observed behavior.  
6. If the implementation violates the documented invariant, make the **smallest** fix, under `src/` only.  
7. Run the complete suite again.  
8. Create **one** draft pull request containing the regression test and the fix. The PR description must list the commands run and their results.

Guardrails to include in the prompt:

- Do not modify dependency manifests (`pom.xml`), workflow files, scripts, documentation, or generated files.  
- Do not weaken, skip, or delete existing tests.  
- If the baseline fails for an infrastructure reason, report it and stop rather than "fixing" infrastructure.

Note in the README that the prompt guardrails are advisory; the **enforced** boundaries are the sandbox, the network allowlist, the read-only token, and `allowed-files: src/**` on the safe output.

### 6.3 sandbox-explorer.lock.yml

- Generated with `gh aw compile sandbox-explorer`. Never hand-edit.  
- If `gh` and the `gh-aw` extension are available in your environment, compile it and commit the output. If not, do **not** fabricate a lock file; leave it out, and make the README and the final summary clearly tell the user to run the compile step.  
- Add a header comment to the `.md` source reminding editors to recompile after changes.

### 6.4 .github/workflows/kvm-probe.yml (optional, recommended)

A tiny hand-written `workflow_dispatch` workflow on `ubuntu-24.04` that checks `/dev/kvm` exists and is accessible (e.g. `ls -l /dev/kvm`, `kvm-ok` via `cpu-checker`, or reading `/proc/cpuinfo` for `vmx|svm`). Purpose: nested virtualization on hosted runners is not officially guaranteed, so users can quickly check before burning a full agent run. Fails clearly with a message pointing to the self-hosted runner notes in the README.

## 7\. Verification Claude Code must perform

Run what you can locally and report results. Do not claim success for steps you could not run.

1. **Build and baseline:** `./scripts/test-in-docker.sh` passes (both seeded tests green). This proves the Maven-in-container → host socket → Testcontainers → PostgreSQL chain works.  
2. **Prove the bug exists (throwaway):** temporarily add a case-variation test, run it via the script, confirm it fails with an assertion like `expected: <false> but was: <true>`, then **remove the test** and confirm `git status` is clean for `src/`. Report the observed failure message.  
3. **Prove the fix is one line (throwaway):** temporarily apply the normalization fix with the case test present, confirm all tests pass, then **revert both**. Report it.  
4. **Lint:** run `shellcheck` on the script if available; YAML-lint the workflow files if a linter is available.  
5. **Compile:** run `gh aw compile sandbox-explorer` if possible (see 6.3).  
6. **Optional local sandbox check:** if `sbx` is installed and logged in, run the same test script inside a sandbox (`sbx run <agent>` in the repo, or the sbx shell template) to show Testcontainers working against the sandbox's private daemon. Skip without failing if `sbx` is unavailable.

Final state on the default branch: seeded tests green, bug present, no case-variation test, no fix.

## 8\. README.md contents

Concise, skimmable. Include:

1. **What this demonstrates** — one paragraph plus the layer diagram:

```
GitHub Actions runner (ubuntu-24.04)
└── Docker Sandbox microVM (own kernel, filesystem, network)
    ├── gh-aw agent (Copilot)
    └── private Docker daemon
        ├── Maven / Java 21 test container
        └── PostgreSQL (Testcontainers)
```

   And the source-to-runtime flow: Markdown workflow → `gh aw compile` → `.lock.yml` → hosted runner → sbx microVM → agent \+ tools.

   

2. **Inside vs outside the boundary** — a small table: inside \= root, any shell command, own Docker daemon; outside \= network allowlist, `contents: read` token, PR via separate safe-output job limited to `src/**`, draft only, human review required.  
3. **The seeded task** — what the requirement says, what the code does, why the existing test misses it. Warn readers not to fix it on `main`.  
4. **Run the tests locally** — `./scripts/test-in-docker.sh` (Docker only).  
5. **Run the agentic workflow** — step by step:  
   - `gh extension install github/gh-aw`  
   - Add secrets `DOCKER_USERNAME` and `DOCKER_PAT` (needed to pull the sandbox template) via repo settings or `gh secret set`.  
   - Copilot access: either a Copilot entitlement plus `copilot-requests: write`, or a `COPILOT_GITHUB_TOKEN` secret per gh-aw docs.  
   - Enable **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests**.  
   - `gh aw compile sandbox-explorer`, commit both `.md` and `.lock.yml`, push.  
   - `gh aw run sandbox-explorer` then `gh run watch`.  
6. **Expected result** — checklist: sbx preflight succeeds; environment evidence in logs; baseline passes; new case test fails; full suite passes after fix; separate job opens a draft PR touching only `src/**`; sandbox cleaned up. Mention the reference run took roughly 11 minutes.  
7. **Runner requirements** — KVM / `/dev/kvm`, passwordless sudo, Docker Engine, apt-based distro; nested virtualization on hosted runners is not officially guaranteed (point to `kvm-probe.yml`); for self-hosted, use Ubuntu 24.04 with KVM, change `runs-on`, recompile. Don't preinstall sbx.  
8. **Try sbx locally** — `sbx login`, `cd` into the repo, `sbx run claude` (or `codex` / `opencode`), give it the same task. Link [https\://docs.docker.com/ai/sandboxes/](https://docs.docker.com/ai/sandboxes/).  
9. **Resetting the demo** — how to close the draft PR / delete the branch so the demo can be rerun.  
10. Credits: link the blog post and the reference repo.
